Reserve resources for a time slot: staff members, rooms, equipment, or
pools of interchangeable units. Reservations can be created by staff, or
scheduled by the customer through a tokenized invitation link — no
account needed.

Features:

- **Reservation types**: duration, availability calendar, booking window
  rules, cancellation deadline, locations where offered.
- **Categories and stage pipelines**: types are grouped in categories;
  each category configures its own ordered stages, mapped to a fixed
  list of states that automation and reporting can rely on.
- **Multiple locations**: locations are partners (addresses with
  timezone); resources are assigned to locations on a schedule — a
  barber can work at shop A on weekdays and shop B on Saturdays.
- **Bookable resources**: staff (users/employees), material resources
  (rooms, courts), and pools of interchangeable units with a quantity (a
  bike fleet, "table seats").
- **Functions**: flat capabilities on resources; a type requires
  functions, and each required role is a leg of the booking filled by a
  matching resource (doctor + exam room).
- **In/out flows**: *IN* reservations happen on-site (appointments,
  multi-day stays); *OUT* reservations take the resource away (rentals),
  with pickup/return instead of check-in.
- **Capacity**: a pool with quantity N serves bookings consuming K units
  — party-size seating and multi-unit rentals share the same mechanism.
- **Lifecycle**: fixed states (pending, scheduled, confirmed, attended,
  cancelled, no-show, picked-up, returned) drive automation; check-in
  and attendance actions; synced ``calendar.event`` for busy time,
  alarms and ICS.
- **Guest scheduling**: pending reservations get a tokenized link the
  requester uses to pick a slot themselves.

Comparison with ``resource_booking``
------------------------------------

This module is an alternative implementation of the problem solved by
``resource_booking`` (in ``oca/calendar``). The two are independent and
can coexist — nothing here depends on it.

Why a fresh implementation
--------------------------

- **License.** The target is LGPL-3 so the app can be reused freely;
  ``resource_booking`` is AGPL-3, and an LGPL addon cannot depend on it.
- **Architecture divergence.** Catalog-first slot search (before any
  record exists), function-leg matching instead of enumerated
  combinations, pools, stage pipelines and locations are all core
  assumptions — retrofitting them into ``resource_booking`` would mean
  surgery on its data model, not extensions on top of it.
- **Still a reference.** Its availability engine's handling of
  timezones, leaves and interval math informed this implementation.

Configuration
=============

To configure this module:

1. **Categories** — go to *Reservations → Configuration → Categories*
   and create the categories grouping your reservation types.
2. **Functions** — in *Configuration → Functions*, create the
   capabilities resources can have (e.g. "Haircut", "Exam room").
3. **Locations** — locations are partners. In *Configuration →
   Locations* (or Contacts), create a partner per site, set its
   timezone, and configure its stage pipeline on the *Reservation
   Pipeline* tab: ordered stages, each mapped to a fixed state (draft,
   scheduled, in progress, done, no-show, cancelled). Slot times are
   displayed in the location's timezone.
4. **Resources** — in *Reservations → Resources*, mark
   ``resource.resource`` records bookable and set their functions,
   quantity (for pools), and location-schedule lines (which location
   they work at, on which calendar). A resource with a single
   always-true line is a fixed-location resource.
5. **Reservation types** — in *Configuration → Reservation Types*, set
   duration, the required roles (one leg each), availability calendar,
   booking window (min notice / max horizon), cancellation deadline,
   locations offered, and message templates.
6. **Blocking time** — create ``resource.calendar.leaves`` on a resource
   (maintenance), on a location calendar (site closed), or globally
   (public holidays). Recurring closures belong in the resource's
   calendar attendance lines instead.

Usage
=====

Creating a reservation
----------------------

1. Go to *Reservations → Reservations* and click *New*.
2. Pick the **type** and **location**, and the customer (**partner**).
3. Fill the role legs: pick a resource for each required role, or leave
   them empty for auto-assignment when the slot is picked.
4. Pick a slot (from availability) or set start/stop directly.

The reservation moves through its category's stages; each stage maps to
a fixed state used by automation and reporting.

Invitation flow (guest self-scheduling)
---------------------------------------

Create a draft reservation with a partner and a type — no slot yet.
Share the tokenized link (from the form). The guest opens the link,
picks a slot from the type's availability, and confirms. No account is
needed.

Check-in and attendance
-----------------------

- **IN** reservations: mark *Attended* when the customer arrives, or
  *No-show* if they don't. OUT reservations use *Picked up* and
  *Returned* instead.
- Check-in drives KPIs and, with the sale module, invoicing.

Cancelling and rescheduling
---------------------------

Cancel from the reservation form or the kanban card — the linked
calendar event is removed automatically. Reschedule by picking a new
slot; the event projection follows.
